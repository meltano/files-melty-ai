# Data Pipelines: Extraction, Loading, and Mapping

How to run EL(T) pipelines with Meltano: extractor/loader configuration, stream/property selection, replication methods, incremental state, inline data mapping, and a condensed end-to-end tutorial.

## Data Integration (EL)

Meltano lets you easily extract and load data from and to databases, SaaS APIs, and file formats using primarily Singer taps and targets, which take the role of your project's extractors and loaders.

Meltano manages your tap and target configuration for you, makes it easy to select which streams and properties to extract, and keeps track of the incremental replication state, so subsequent pipeline runs with the same state ID always pick up right where the previous run left off.

You run EL(T) pipelines using `meltano run`.

### Plugin configuration

`meltano run` determines the configuration of your extractor + loader pairs and any optional utilities (e.g. dbt) by looking in the environment, your project's `.env` file, the system database, and finally your `meltano.yml` project file, falling back to a default value if nothing was found.

Use `meltano config list <plugin>` to list all available settings with their names, environment variables, and current values. `meltano config print <plugin>` prints the current configuration in JSON format. If supported by the plugin type, configuration can be tested using `meltano config test <plugin>`.

### Extractor catalog generation

Many extractors (Singer taps) expect to be provided a catalog when run in sync mode using `meltano run` or `meltano invoke`. This catalog is a JSON file describing the schemas of the available streams and properties, along with metadata to indicate which streams and properties should (or should not) be extracted.

A catalog can be generated by running the extractor in discovery mode and making the desired modifications to the schemas and metadata for the discovered streams and properties. Because these catalog files can be very large and can get outdated as data sources evolve, this process can be tedious and error-prone.

Meltano can handle catalog generation for you, letting you describe your desired modifications using stream selection, metadata, and schema rules that can be configured like any other setting, and applied to the discovered catalog on the fly when the extractor is run using `meltano run` or `meltano invoke`.

To manually inspect the generated catalog for debugging purposes, dump it to STDOUT or a file using the `--dump=catalog` option on `meltano invoke` or `meltano el`.

If you've already manually discovered a catalog and modified it to your liking, it can be provided explicitly using `meltano el`'s `--catalog` option or the `catalog` extractor extra.

In some cases, like when a tap has extra command line options like `--about` or `--version` that don't need a catalog, or when you only need to dump the tap configuration with `--dump=config`, Meltano avoids running discovery to save the overhead and to not require the tap to be configured with valid credentials.

### Selecting streams and properties for extraction

Extractors are often capable of extracting many more streams and properties than your use case requires. To save on bandwidth and storage, it's usually a good idea to instruct your extractor to only select the streams and properties you actually plan on using.

Meltano provides several configuration options for controlling stream and property selection, each serving different purposes:

#### `select` vs `select_filter`

**`select`** (the `select` extractor extra) defines which streams and properties to extract from the **discovered or provided catalog**. Use this when you want fine-grained control over which specific properties within streams are included or excluded:

- Supports both stream-level patterns (e.g., `users`) and property-level patterns (e.g., `users.email`)
- Applied **only when no custom `catalog` is provided**
- Controls selection at the property level within streams
- Configured via `meltano select` or `select:` in `meltano.yml`

**`select_filter`** filters **entire streams** at runtime and is always applied regardless of whether a custom catalog is provided:

- Only supports stream-level patterns (e.g., `users`, `!logs`)
- Applied **even when a custom `catalog` is provided**
- Set via `--select` and `--exclude` flags on `meltano run` or `meltano el`
- Useful for temporarily filtering streams without modifying `select` configuration

**Key difference**: `select_filter` is applied to the **provided catalog** (whether custom or discovered), while `select` is used to build the catalog from discovery results.

#### `catalog`, `schema`, and `metadata`

**`catalog`** (the `catalog` extractor extra) provides a **pre-built catalog file** that completely bypasses discovery:

- When set, Meltano uses this file instead of running discovery
- `select` and `schema` rules are **not applied** to custom catalogs
- `metadata` rules are **not applied** to custom catalogs
- `select_filter` **is still applied** to filter streams at runtime

**`schema`** (the `schema` extractor extra) **modifies stream schemas** in the discovered catalog:

- Allows overriding or adding JSON Schema definitions for properties
- Applied **only to discovered catalogs** (not custom catalogs)
- Supports wildcards to match multiple streams/properties
- Useful for adding missing properties or changing property types

**`metadata`** (the `metadata` extractor extra) sets **stream and property metadata** in the discovered catalog:

- Controls replication methods, replication keys, and other Singer metadata
- Applied **only to discovered catalogs** (not custom catalogs)
- Supports wildcards to match multiple streams/properties
- Used primarily for database extractors to configure replication behavior

Meltano makes it easy to select specific streams and properties for inclusion or exclusion using `meltano select` and the `select` extractor extra, letting you specify inclusion and exclusion rules that can contain Unix shell-style wildcards to match multiple streams and/or properties at once.

Exclusion takes precedence over inclusion: if a stream or property is matched by an exclusion pattern, there's no way to get it back using an inclusion pattern unless the exclusion pattern is manually removed from `meltano.yml` first.

If no rules are defined using `meltano select`, Meltano falls back on the catch-all rule `*.*` so that all streams and properties are selected.

```bash
meltano select <plugin> --list --all

# For example:
meltano select tap-gitlab --list --all
```

```bash
meltano select <plugin> <stream> <property>
meltano select <plugin> --exclude <stream> <property>

# For example:
meltano select tap-gitlab commits id
meltano select tap-gitlab commits project_id
meltano select tap-gitlab commits created_at
meltano select tap-gitlab commits author_name
meltano select tap-gitlab commits message

# Include all properties of a stream
meltano select tap-gitlab tags "*"

# Exclude matching properties of all streams
meltano select tap-gitlab --exclude "*" "*_url"
```

This adds the selection rules to `meltano.yml`:

```yaml title="meltano.yml"
        extractors:
          - name: tap-gitlab
            config:
              projects: meltano/meltano meltano/tap-gitlab
              start_date: "2024-03-01T00:00:00Z"
            select:
              - commits.id
              - commits.project_id
              - commits.created_at
              - commits.author_name
              - commits.message
              - tags.*
              - "!*.*_url"
```

### Setting metadata

Additional Singer stream and property metadata (like `replication-method` and `replication-key`) can be specified using the `metadata` extractor extra, treated like a `_metadata` setting with nested properties `_metadata.<stream>.<key>` and `_metadata.<stream>.<property>.<key>`.

```bash
meltano config set <plugin> _metadata <stream> replication-method <LOG_BASED|INCREMENTAL|FULL_TABLE>

# For example:
meltano config set tap-postgres _metadata some_stream_id replication-method INCREMENTAL
meltano config set tap-postgres _metadata other_stream replication-method FULL_TABLE
```

This adds the metadata rules to `meltano.yml`:

```yaml title="meltano.yml"
        extractors:
          - name: tap-postgres
            metadata:
              some_stream_id:
                replication-method: INCREMENTAL
                replication-key: id
              other_stream:
                replication-method: FULL_TABLE
```

You can also set `replication-method` metadata for all streams or matching streams at once using wildcards:

```bash
# Set replication-method metadata for all streams
meltano config set tap-postgres _metadata '*' replication-method INCREMENTAL

# Set replication-method metadata for matching streams
meltano config set tap-postgres _metadata '*_full' replication-method FULL_TABLE
```

```yaml title="meltano.yml"
        extractors:
          - name: tap-postgres
            metadata:
              "*":
                replication-method: INCREMENTAL
              "*_full":
                replication-method: FULL_TABLE
```

> **Order matters when declaring metadata rules.** The last rule that matches a stream or property is used. In the example above, if a stream matches both rules, the `replication-method` will be set to `FULL_TABLE`. This might change in the future, when metadata rules are applied in increasing order of specificity.

#### Overriding key properties and replication keys

You can also use the `metadata` extra to override the `key-properties` (the columns that uniquely identify a record) and the `replication-key` (the column used as a bookmark for incremental replication) for a stream. Replace `some_stream_id` with the stream identifier from the extractor's discovered catalog. This is useful when the discovered catalog does not correctly identify these values, or when you need to change them for a specific use case.

```bash
# Override key-properties for a stream
meltano config set tap-postgres _metadata some_stream_id key-properties '["id"]'

# Override replication-key for a stream
meltano config set tap-postgres _metadata some_stream_id replication-key updated_at
```

```yaml title="meltano.yml"
        extractors:
          - name: tap-postgres
            metadata:
              some_stream_id:
                replication-method: INCREMENTAL
                replication-key: updated_at
                key-properties:
                  - id
```

### Overriding schemas

A `schema` extractor extra lets you easily override Singer stream schema descriptions. Unix shell-style wildcards can be used to match multiple streams and/or properties at once.

## Replication methods

Extractors can replicate data from a source using one of the following methods:

- Log-based Incremental Replication
- Key-based Incremental Replication
- Full Table Replication

Extractors for SaaS APIs typically hard-code the appropriate replication method for each supported stream. Most database extractors, on the other hand, support two or more of these methods and require you to choose an appropriate option for each table through the `replication-method` stream metadata key.

To support incremental replication, where a pipeline run picks up where the previous run left off, Meltano keeps track of incremental replication state.

### Log-based Incremental Replication

- `replication-method` stream metadata value: `LOG_BASED`

The extractor uses the database's binary log files to identify what records were inserted, updated, and deleted from the table since the last run (if any), and extracts only these records. Not supported by all databases and database extractors.

### Key-based Incremental Replication

- `replication-method` stream metadata value: `INCREMENTAL`

The extractor uses the value of a specific column on the table (the Replication Key, e.g. an `updated_at` timestamp or incrementing `id` integer) to identify what records were inserted or updated (but not deleted) since the last run (if any), and extracts only those records.

#### Replication Key

Replication Keys are columns that database extractors use to identify new and updated data for replication. When you set a table to use Key-based Incremental Replication, you'll also need to define a Replication Key by setting the `replication-key` stream metadata key (see "Overriding key properties and replication keys" above).

### Full Table Replication

- `replication-method` stream metadata value: `FULL_TABLE`

The extractor extracts all available records in the table on every run.

## Incremental replication state

Most extractors (Singer taps) generate state when run, which can be passed along with a subsequent invocation to have the extractor pick up where it left off the previous time (handled automatically for `meltano run` and with the `--state-id` argument for `meltano el`).

Meltano stores this pipeline state in its state backend, identified by the `meltano run` State ID, automatically generated based on the extractor name, loader name, and active environment name.

To manually inspect a job's state for debugging purposes, or store it somewhere other than the system database, use the `meltano state` command (list all states, get state by name, set state, etc.).

### Start date and incremental replication

When using incremental replication, the bookmark dates stored in the state take precedence over the `start_date` configuration setting. If you change `start_date` to an earlier date hoping to pull more historical data, the extractor will still start from where it left off according to the saved state.

To pull historical data from before the bookmarked date, perform a full refresh using the `--full-refresh` flag:

```bash
# This will ignore the saved state and use the configured start_date
meltano run --full-refresh tap-gitlab target-postgres

# Or with meltano el
meltano el tap-gitlab target-postgres --full-refresh
```

The `--full-refresh` flag tells Meltano to ignore any previously saved state and start fresh from the configured `start_date`. After the full refresh completes, the state is updated with the new bookmarks, and subsequent runs continue incrementally from that point.

Alternatively, you can directly manage the state using the `meltano state` command.

### Internal State Merge Logic

When running Extract and Load pipelines via `run`, Meltano retrieves your pipeline state for the most recently completed pipeline based on State ID. If a state record from a completed job is found, its data is passed along to the extractor.

If the most recent pipeline aborted before a particular stream completed, it might have generated a partial state record. If one or more partial state records are found, the partial data is merged with the last completed state, producing an up-to-date state artifact passed to the extractor. This allows your pipeline to pick up where it left off even if the last sync aborted midway through.

The same merge behavior applies when a user runs `meltano state get`, which returns the merged result of the latest completed state plus any newer partial state records, if they exist. This works because Singer Targets are expected to emit STATE messages only after persisting data for a given stream.

Partial state records can also be inserted manually via `meltano state merge`. Unlike `meltano state merge`, `meltano state set` inserts a complete record, causing Meltano to ignore any previous state records, whether completed or partial.

> **Not seeing state picked up after a failed run?** Some loaders only emit state once their work is completely done, even if some data may have been persisted already, and even if earlier state messages from the extractor could have been forwarded to Meltano. When a pipeline with such a loader fails or is otherwise interrupted, no state will have been emitted yet, and a subsequent ELT run will not be able to pick up where this run actually left off.

### Pipeline-specific configuration

To specify (or override) the values of certain settings at runtime, on a per-pipeline basis, set them in the `meltano run` execution environment using environment variables.

This lets you use the same extractors and loaders in multiple pipelines, configured differently each time, as an alternative to creating multiple configurations using plugin inheritance.

```bash
export TAP_FOO_BAR=bar
export TAP_FOO_BAZ=baz

# For example overriding a start date
export TAP_GITHUB_START_DATE="2023-01-01"

meltano run ...

TAP_FOO_BAR=bar TAP_FOO_BAZ=baz meltano run ...
```

To verify these environment variables will be picked up as intended, test with `meltano config print <plugin>` before running `meltano run`.

## Running pipelines with `elt`

Originally the `elt` command was the only way to run pipelines, but the `run` command has become the recommended approach for most use cases due to its flexibility. For some use cases the `elt` command is still preferred because it has more fine-grained control for extract + load pairs.

### Incremental replication state (elt)

For `meltano el`, the State ID has to be created and set manually using the `--state-id` argument; use a unique string identifier for the pipeline and always include it, since it must be present in each execution for incremental replication to work.

If you already have a state file you'd like to use, it can be provided explicitly using `meltano el`'s `--state` option or the `state` extractor extra.

### Pipeline-specific schedule configuration

If you're using the `elt` syntax with `meltano schedule` to schedule your pipelines, you can specify environment variables for each pipeline in `meltano.yml`, where each entry in the `schedules` array can have an `env` dictionary:

```yaml title="meltano.yml"
schedules:
- name: foo-to-bar
  extractor: tap-foo
  loader: target-bar
  transform: skip
  interval: '@hourly'
  env:
    TAP_FOO_BAR: bar
    TAP_FOO_BAZ: baz
```

Different runners and execution/orchestration platforms have their own way of specifying environment variables along with a command invocation. Airflow's `BashOperator`, for example, supports an `env` parameter:

```python
BashOperator(
    # ...
    bash_command="meltano el ...",
    env={
        "TAP_FOO_BAR": "bar",
        "TAP_FOO_BAZ": "baz",
    },
)
```

### Pipeline environment variables

To allow loaders and transformers to adapt their configuration and behavior based on the extractor and loader they're run with, `meltano el` dynamically sets a number of pipeline-specific environment variables before compiling their configuration and invoking their executables.

#### Extractor variables

Available to loaders _and_ transformers:

- `MELTANO_EXTRACTOR_NAME`: the extractor's `name`, e.g. `tap-gitlab`
- `MELTANO_EXTRACTOR_NAMESPACE`: the extractor's `namespace`, e.g. `tap_gitlab`
- `MELTANO_EXTRACT_<SETTING_NAME>`: one environment variable for each of the extractor's settings and extras, e.g. `MELTANO_EXTRACT_PRIVATE_TOKEN` for the `private_token` setting, and `MELTANO_EXTRACT__LOAD_SCHEMA` for the `load_schema` extra
- `<SETTING_ENV>`: all of the extractor's regular configuration environment variables, as listed by `meltano config list <plugin>`, e.g. `TAP_GITLAB_API_URL` for the `api_url` setting

#### Loader variables

Available to transformers:

- `MELTANO_LOADER_NAME`: the loader's `name`, e.g. `target-postgres`
- `MELTANO_LOADER_NAMESPACE`: the loader's `namespace`, e.g. `postgres`
- `MELTANO_LOAD_<SETTING_NAME>`: one environment variable for each of the loader's settings and extras, e.g. `MELTANO_LOAD_SCHEMA` for the `schema` setting, and `MELTANO_LOAD__DIALECT` for the `dialect` extra
- `<SETTING_ENV>`: all of the loader's regular configuration environment variables, as listed by `meltano config list <plugin>`, e.g. `TARGET_POSTGRES_HOST` for the `host` setting

#### Transform variables

Available to transformers:

- `MELTANO_TRANSFORM_NAME`: the loader's `name`, e.g. `tap-gitlab`
- `MELTANO_TRANSFORM_NAMESPACE`: the loader's `namespace`, e.g. `tap_gitlab`
- `MELTANO_TRANSFORM_<SETTING_NAME>`: one environment variable for each of the transform's settings and extras, e.g. `MELTANO_TRANSFORM__PACKAGE_NAME` for the `package_name` extra

#### How to use

Inside your loader or transformer's `config` object in `meltano.yml`, reference these (and other) environment variables as `$VAR` (as a single word) or `${VAR}` (inside a word). Inside your plugin, reference them through `os.environ` as usual (assuming Python).

This feature dynamically configures the `target-postgres` and `target-snowflake` loaders and the `dbt` transformer, independent of the specific extractor and loader used:

- Default value for the `target-postgres` and `target-snowflake` `schema` settings: `$MELTANO_EXTRACT__LOAD_SCHEMA` (e.g. `tap_gitlab` for `tap-gitlab`)
- Default value for `dbt`'s `target` setting: `$MELTANO_LOAD__DIALECT` (e.g. `postgres` for `target-postgres` and `snowflake` for `target-snowflake`, corresponding to the target names in `transform/profile/profiles.yml`)
- Default value for `dbt`'s `models` setting: `$MELTANO_TRANSFORM__PACKAGE_NAME $MELTANO_EXTRACTOR_NAMESPACE my_meltano_model`, e.g. `tap_gitlab tap_gitlab my_meltano_model` for the `tap-gitlab` transform and `tap-gitlab` extractor

## Inline Data Mapping (Mappers)

Meltano lets you alter data passing through your EL pipelines to do precisely what you need for your use case. Although commonly users want to replicate their data in the most raw format (ELT vs ETL), there are many use cases that require minor alterations to data on the fly. This is where mappers, also referred to as inline stream maps, come in.

### Features

Mapper features fall into two categories: stream level or property (record) level.

**Stream Level:**
- Aliasing: streams can be aliased to provide custom naming downstream.
- Filtering: stream records can be filtered based on any user-defined logic.
- Duplication: streams can be split or duplicated and then sent as multiple distinct streams to the downstream target.

**Property (Column) Level:**
- Aliasing: properties can be renamed in the resulting stream, e.g. altering a column name from `id` -> `customer_id`
- Transformations: properties can be transformed inline, e.g. upper casing, casting types, etc.
- Exclusions: properties can be removed from the resulting stream.
- Additions: new properties can be created based on inline user-defined expressions.
- Flatten nested properties: separates large complex properties into multiple distinct fields.

**Out of scope:**
- Mappers do not support aggregation. To aggregate data, first land the data in your destination and then apply aggregations using a transformation plugin like dbt.
- Mappers do not support joins between streams. To join data, first land the data and then perform joins using a transformation tool like dbt.
- Mappers do not support external API lookups. To add external API lookups, either (a) land all your data and then join using a transformation plugin like dbt, or (b) create a custom mapper plugin with inline lookup logic.

### Use cases

**PII hashing or removal.** Some users have strict requirements to not store any raw PII data in their destination system. Mappers can hash PII data on the fly so it arrives in your destination but not in plain text, or simply remove it. If you need to remove PII entirely you can also consider using selection criteria to avoid replicating it in the first place, but mappers give more precision if needed.

**Altering tap behavior.** Sometimes a tap from MeltanoHub provides the data you want but not in the custom format you need. Two options: (1) fork the tap and maintain the new variant, or (2) use mappers to alter the output of the generic tap without editing the tap itself.

**Renaming streams.** Mappers let you make stream-level alterations like renaming, duplicating, or splitting a stream — enforcing consistent naming conventions for tables in your warehouse, or duplicating a stream to add mapper alterations while preserving the original. Useful for reverse ETL use cases where the target expects data in streams and fields named a particular way.

**Other uses:** modifying primary keys, splitting streams, filtering records based on conditions, type casting, casing updates, coalescing values.

### Running mappers

There are two ways to use mapper functionality:

1. Install a standalone mapper plugin that runs between a tap and a target, e.g. `meltano run tap-csv <MAPPER> target-jsonl`.
2. If either your tap or target is based on the Meltano SDK, configure the `stream_map_config` settings in the plugin configuration (inline stream maps).

#### SDK Stream Maps

If either your tap or target is built on the Meltano SDK, it automatically has mapper features built in (inline stream maps). This is the easiest way to get mapper functionality into your pipeline, avoiding some of the limitations of standalone mappers (requires installing another plugin, isn't supported by `meltano el`, etc.). The limitation is that the mapper functionality is baked into the SDK, so customizations are less flexible relative to standalone mappers where you can create your own forks.

Example: the SDK-based `meltanolabs` variant of `tap-github` configured to lowercase all repo names in the issues stream:

```yaml title="meltano.yml"
  - name: tap-github
    variant: meltanolabs
    pip_url: meltanolabs-tap-github
    config:
      stream_maps:
        issues:
          repo: record['repo'].lower()
```

For more details and examples refer to the SDK documentation.

#### Standalone Mapper Plugins

The other way to get mapper functionality is a standalone mapper plugin inserted between your tap and target to do the translation: `meltano run tap-csv <MAPPER> target-jsonl`. These can be used even when your tap and/or target are not SDK based.

The advantage relative to SDK inline stream maps is that you can fork the mapper plugin or build your own to do whatever you need. A limitation is that currently you can't run these with `meltano el`.

The two most common mapper plugins are:

- `meltano-map-transform` (MeltanoLabs)
- `pipelinewise-transform-field` (transferwise)

These can be added like any other plugin:

```bash
meltano add mapper <mapper name>

# Example
meltano add mapper meltano-map-transformer
```

You can also debug a mapper in isolation by manually piping Singer messages into it:

```bash
# Output raw Singer messages to a file
meltano invoke tap-x > output.json

# Pipe them into the mapper using invoke
cat output.json | meltano invoke mapping_name
```

Example, from the `meltano-map-transformer` repository, altering casing of the data. Given this input CSV and mapper configuration:

```csv
id,first_name,last_name,email,ip_address
1,Ethe,Book,ebook0@twitter.com,67.61.243.220
```

```yaml title="meltano.yml"
plugins:
  mappers:
  - name: meltano-map-transformer
    variant: meltano
    pip_url: meltano-map-transform
    mappings:
    - name: lower
      config:
        stream_maps:
          customers:
            __alias__: customers_v5
            first_name: first_name.lower() # three different ways of accessing the variable
            last_name: record['last_name'].lower()
            email:  _['email'].upper()
            count_t: str(last_name.count("t")) # need to cast to str because it could be NULL!
            ip_address: __NULL__
```

After running `meltano run tap-csv lower target-sqlite`, the result:

| count_t | email              | first_name | id  | last_name | __loaded_at             |
| -------- | ------------------ | ----------- | --- | ---------- | -------------------------- |
| 0        | EBOOK0@TWITTER.COM | ethe        | 1   | book       | 2023-03-17 16:57:19.095880 |

### FAQs

**Can I use standalone mapper plugins with the `meltano el` command?** No, currently only `meltano run` and `meltano invoke` support standalone mapper plugins.

**Can I use mapping features with the BATCH message type?** No, BATCH message type does not currently support mapping functionality.

**When would I use standalone mapper plugins vs SDK based stream maps?** Mostly preference, but trade-offs to consider:

- Mappers work for SDK and non-SDK connectors. If your pipeline uses two non-SDK connectors, mappers are your best option.
- SDK stream maps are part of the SDK, which inherently makes them more difficult to change. If you need custom functionality, forking a mapper plugin and customizing it is your best option.
- SDK stream maps avoid installing an additional plugin into your project.
- Mapper plugins alter data after it's been extracted, whereas SDK-based stream maps on the tap side could alter extraction behavior. Depending on your use case (e.g. deleting streams), it might be slightly more efficient to do it in the tap and avoid extracting unneeded data.
- Mapper plugins aren't supported by `meltano el`.

**Do both my tap and target need to support SDK based stream maps?** No, you only need one of your plugins to be SDK based to get this functionality.

## Complete ELT Walkthrough (Condensed)

An end-to-end example, from install to a scheduled, transformed, analyzed pipeline.

### Install Meltano

Requires Linux, macOS, or Windows, and Python 3.10, 3.11, 3.12, 3.13, or 3.14. Recommended to install into a dedicated Python virtual environment inside the directory holding your Meltano projects.

```bash
mkdir meltano-projects
cd meltano-projects

# Install uv
curl -LsSf https://astral.sh/uv/install.sh | sh

# Install meltano from PyPI
uv tool install meltano

# Optionally specify Python version
uv tool install --python <desired Python version> meltano

# Verify
meltano --version
```

### Create your Meltano project

```bash
mkdir meltano-projects
cd meltano-projects

meltano init <project directory path>

# For example:
meltano init my-meltano-project

# If using Docker, mount the current working directory:
docker run -v $(pwd):/projects -w /projects meltano/meltano init my-meltano-project
```

This creates a new directory with, among other things, your `meltano.yml` project file:

```yml
default_environment: dev
project_id: <random UUID>
environments:
- name: dev
- name: staging
- name: prod
```

`meltano.yml` doesn't define any plugins or pipeline schedules yet, but does include 3 environments you can use if you wish. Anonymous usage stats are enabled by default.

```bash
cd <project directory>

# For example:
cd my-meltano-project
```

Optionally initialize a Git repository:

```bash
git init
git add --all
git commit -m 'Initial Meltano project'
```

### View and activate your environments

```bash
meltano environment list

export MELTANO_ENVIRONMENT=dev
# or, PowerShell:
# $env:MELTANO_ENVIRONMENT="dev"

# optional: add a new environment
meltano environment add <environment name>
```

Alternatively include `--environment=dev` on each `meltano` command. You'll see a log message `Environment 'dev' is active` on each run.

### Add an extractor

1. Check whether an extractor for your source is supported out of the box (MeltanoHub Extractors list).
2. If supported out of the box, add it:

```bash
meltano add <plugin name>

# For example:
meltano add tap-gitlab

# Choose a non-default variant:
meltano add tap-gitlab --variant=singer-io

# Docker:
docker run -v $(pwd):/project -w /project meltano/meltano add tap-gitlab
```

This adds the plugin to `meltano.yml`:

```yml
plugins:
  extractors:
  - name: tap-gitlab
    variant: meltanolabs
    pip_url: git+https://github.com/MeltanoLabs/tap-gitlab.git
```

A `plugins/extractors/tap-gitlab--meltanolabs.lock` file is also added — this pins your settings definitions for stability and should be checked into git. For additional stability, pin `pip_url` to a specific release version or commit hash.

3. If not yet discoverable, check MeltanoHub for Singer for an existing Singer tap. If one exists, add it as a custom plugin:

```bash
meltano add --custom <tap name>

# For example:
meltano add --custom tap-covid-19
```

Meltano asks additional questions about the plugin, then adds it:

```yml
plugins:
  extractors:
    - name: tap-covid-19
      namespace: tap_covid_19
      pip_url: tap-covid-19
      executable: tap-covid-19
      capabilities:
        - catalog
        - discover
        - state
      settings:
        - name: api_token
        - name: user_agent
        - name: start_date
```

If no Singer tap exists yet, build your own (see the "Create and Use a Custom Extractor" tutorial), then add it as a custom plugin using a local directory path or Git repository URL.

4. Verify installation:

```bash
meltano invoke <plugin> --help

# For example:
meltano invoke tap-gitlab --help
```

#### Select entities and attributes to extract

By default, Meltano instructs extractors to extract all supported entities and attributes, but it's recommended to specify the ones you actually want.

```bash
meltano select <plugin> --list --all

# For example:
meltano select tap-gitlab --list --all
```

If this fails, the tap likely doesn't support catalog discovery mode and will always extract everything.

```bash
meltano select <plugin> <entity> <attribute>
meltano select <plugin> --exclude <entity> <attribute>

# For example:
meltano select tap-gitlab commits id
meltano select tap-gitlab commits project_id
meltano select tap-gitlab commits created_at
meltano select tap-gitlab commits author_name
meltano select tap-gitlab commits message

# Include all attributes of an entity
meltano select tap-gitlab tags "*"

# Exclude matching attributes of all entities
meltano select tap-gitlab --exclude "*" "*_url"
```

Entity and attribute identifiers can contain wildcards (`*`). This adds the selection rules to `meltano.yml`:

```yml
plugins:
  extractors:
    - name: tap-gitlab
      variant: meltanolabs
      pip_url: git+https://github.com/MeltanoLabs/tap-gitlab.git
environments:
  - name: dev
    config:
      plugins:
        extractors:
          - name: tap-gitlab
            config:
              projects: meltano/meltano meltano/tap-gitlab
              start_date: "2024-03-01T00:00:00Z"
            select:
              - commits.id
              - commits.project_id
              - commits.created_at
              - commits.author_name
              - commits.message
              - tags.*
              - "!*.*_url"
```

Exclusion takes precedence over inclusion — if an attribute is excluded, there's no way to include it back without removing the exclusion pattern.

Verify with `meltano select <plugin> --list`.

#### Choose how to replicate each entity

If pulling from a database source (PostgreSQL, MongoDB, etc.), your extractor likely requires setting a replication method for each selected entity via the `replication-method` stream metadata key. SaaS API extractors typically hard-code the appropriate method per entity, so you can skip this.

- `LOG_BASED`: uses binary log files to identify inserts/updates/deletes since last run. Not supported by all databases.
- `INCREMENTAL`: uses a Replication Key column (e.g. `updated_at` or an incrementing `id`) to identify inserted/updated (not deleted) records since last run.
- `FULL_TABLE`: extracts all available records every run.

```bash
meltano config set <plugin> _metadata <entity> replication-method <LOG_BASED|INCREMENTAL|FULL_TABLE>

# For example:
meltano config set tap-postgres _metadata some_entity_id replication-method INCREMENTAL
meltano config set tap-postgres _metadata other_entity replication-method FULL_TABLE

# Set replication-method metadata for all entities
meltano config set tap-postgres _metadata '*' replication-method INCREMENTAL

# Set replication-method metadata for matching entities
meltano config set tap-postgres _metadata '*_full' replication-method FULL_TABLE
```

If you've set a table's `replication-method` to `INCREMENTAL`, also choose a Replication Key:

```bash
meltano config set <plugin> _metadata <entity> replication-key <column>

# For example:
meltano config set tap-postgres _metadata some_entity_id replication-key updated_at
meltano config set tap-postgres _metadata some_entity_id replication-key id
```

```yml
environments:
  - name: dev
    config:
      plugins:
        extractors:
          - name: tap-postgres
            metadata:
              some_entity_id:
                replication-method: INCREMENTAL
                replication-key: id
              other_entity:
                replication-method: FULL_TABLE
              "*":
                replication-method: INCREMENTAL
              "*_full":
                replication-method: FULL_TABLE
```

Verify by dumping the generated catalog:

```bash
meltano invoke --dump=catalog <plugin>

# For example:
meltano invoke --dump=catalog tap-postgres
```

### Run a data integration (EL) pipeline

```bash
meltano run <extractor> <loader>

# For example:
meltano run tap-gitlab target-postgres
```

If configured correctly, data flows from source into destination. Check your Postgres instance for the tables `warehouse.schema.commits` and `warehouse.schema.tags`.

If the command fails and it's not obvious why, enable debug mode for more insight (see `troubleshooting-and-debugging.md`).

Running `meltano run` again automatically picks up where the previous run left off, assuming the extractor supports incremental replication and you have an active environment. Meltano tracks state using a State ID auto-generated from extractor name, loader name, and active environment name. Use `--full-refresh` or `MELTANO_RUN_FULL_REFRESH=1` to override state and extract everything from the beginning again.

To view state generated by the most recent run:

```bash
meltano state get dev:tap-gitlab-to-target-postgres
```

There's also `meltano el`, a more rigid command for running only EL pipelines, and `meltano invoke`, which executes a single plugin at a time (useful for debugging a failing extractor or loader).

#### Schedule pipelines to run regularly

Meltano supports scheduled pipelines orchestrated using Apache Airflow.

```bash
meltano schedule add <pipeline name> --extractor <extractor> --loader <loader> --interval <interval>

# For example:
meltano schedule add gitlab-to-postgres --extractor tap-gitlab --loader target-postgres --interval @daily
```

The `pipeline name` argument corresponds to the `--state-id` option on `meltano el`, which identifies related EL runs for incremental replication state. To have scheduled runs pick up where an earlier manual run left off, use the same pipeline name.

This adds the schedule to `meltano.yml`:

```yml
schedules:
  - name: gitlab-to-postgres
    extractor: tap-gitlab
    loader: target-postgres
    transform: skip
    interval: "@daily"
```

> The `name` setting in schedules acts as the `state_id` so that state is preserved across scheduled executions. This should generally be a globally unique string based on the job being run (e.g. `gitlab-to-postgres` or `gitlab-to-postgres-prod` if you have multiple environments).

Verify and run manually:

```bash
meltano schedule list

meltano schedule run
```

Add Airflow to manage the schedule and execute the appropriate `meltano run` commands:

```bash
meltano add airflow  # Automatically detected as utility
```

This adds the plugin to `meltano.yml`:

```yml
plugins:
  utilities:
    - name: airflow
      pip_url: git+https://github.com/meltano/airflow-ext.git@main apache-airflow==2.10.5 --constraint https://raw.githubusercontent.com/apache/airflow/constraints-2.8.1/constraints-no-providers-${MELTANO__PYTHON_VERSION}.txt
```

It also automatically adds a `meltano run` DAG generator to `orchestrate/dags`, where Airflow looks for DAGs by default.

```bash
meltano invoke airflow scheduler

# Add `-D` to run the scheduler in the background:
meltano invoke airflow scheduler -D
```

Verify a DAG was created for each scheduled pipeline via the Airflow web interface:

```bash
meltano invoke airflow webserver

meltano invoke airflow webserver -D
```

Create an admin user:

```bash
meltano invoke airflow users create --username melty \
--firstname melty \
--lastname meltano \
--role Admin \
--password melty \
--email melty@meltano.com
```

The web interface and DAG overview are available at http://localhost:8080.

#### Transform loaded data for analysis

See `transformation-and-orchestration.md` for the full dbt integration guide. Quick version:

```bash
meltano add dbt-postgres

meltano config list dbt-postgres

meltano config set dbt-postgres host localhost
meltano config set dbt-postgres user meltano
meltano config set dbt-postgres password meltano
meltano config set dbt-postgres port 5432
meltano config set dbt-postgres dbname warehouse
meltano config set dbt-postgres schema analytics
```

After dbt is installed and configured, `/transform` is populated with dbt artifacts (via the dbt file bundle). Write dbt models in `/transform/models`, typically starting with a `source.yml` defining source tables:

```bash
mkdir ./transform/models/tap_gitlab
touch  ./transform/models/tap_gitlab/source.yml
```

```yaml
config-version: 2
version: 2
sources:
  - name: tap_gitlab
    schema: public
    tables:
      - name: commits
      - name: tags
```

The Meltano convention is to name the model directory after the extractor using snake_case (e.g. `tap_gitlab`). Then add a model file, e.g. `/transform/models/tap_gitlab/commits_last_7d.sql`:

```bash
touch  ./transform/models/tap_gitlab/commits_last_7d.sql
```

```sql
{{
  config(
    materialized='table'
  )
}}

select *
from {{ source('tap_gitlab', 'commits') }}
where created_at::date >= current_date - interval '7 days'
```

Run via `meltano invoke` or `meltano run`:

```bash
meltano invoke dbt-postgres:<command>

# For example:
meltano invoke dbt-postgres:run
```

```bash
meltano run <extractor> <loader> <other_plugins>

# For example:
meltano run tap-gitlab target-postgres dbt-postgres:test dbt-postgres:run tap-postgres target-gsheet
```

After the transform run completes, a new table named after your model appears, e.g. `warehouse.analytics.commits_last_7d`. Other supported dbt commands: `dbt-postgres:test`, `dbt-postgres:seed`, `dbt-postgres:snapshot`, and selection criteria like `dbt-postgres:run --models tap_gitlab.*`.
